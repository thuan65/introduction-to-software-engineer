# ADR-002: Use PostgreSQL with Exclusion Constraints and Row-Level Locking for Booking Integrity

- Status: accepted

## Context
Preventing double-bookings (BR-05, UC-04) is functional and reliability requirement (DG-01, NFR-06). When First-Come-First-Served auto-approval is active (UC-12), simultaneous booking requests for the same room and time slot can create race conditions (Risk R2). Additionally, conflict checks must execute within 100 ms (NFR-03) and search results must reflect cancellations immediately (NFR-05).

## Decision
Use PostgreSQL hosted on Supabase Cloud in production and containerized via Docker in local development as the single source of truth. Enforce booking integrity at both the application and database levels by wrapping conflict checks and insertions inside atomic transactions with row-level locking, backed by a PostgreSQL GiST exclusion constraint for bookings.

## Alternatives Considered
1. MySQL / SQLite: Rejected because SQLite lacks robust concurrent row-level locking, and MySQL lacks native GiST range-overlap exclusion constraints required to prevent overlapping reservations at the database level.

## Consequences
- Positive:
  - Ensures zero double-bookings under concurrent FCFS bursts (DG-01).
  - Keeps conflict queries under 100 ms via GiST/B-tree indexes (NFR-03).
  - Ensures immediate search consistency without cache sync overhead (DG-02).
  - Fits within Supabase's free tier.
- Negative:
  - Requires enabling the btree_gist PostgreSQL extension during database migration setup.
