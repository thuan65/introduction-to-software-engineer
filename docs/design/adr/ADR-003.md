# ADR-003: Integrate Locally Hosted VLM Behind an Interface with Keyword-Search Fallback

- Status: accepted

## Context
The system provides an optional AI assistant for natural language room search (FR-14), floor-plan Q&A (FR-15), and conversational booking (FR-16). However, project budget constraints prohibit recurring cloud AI API fees, and running a VLM on library workstation hardware introduces latency and memory-exhaustion risks (Risk R1, DG-07).

## Decision
Host the Vision-Language Model locally on the library staff workstation wrapped in a lightweight Python HTTP REST API, accessed by the Django backend through an abstracted IVLMClient interface . Implement a strict timeout and health check in so that if the VLM is offline or slow, the system gracefully falls back to standard text-based keyword search via (DG-07).

## Alternatives Considered
1. Commercial Cloud VLM APIs (OpenAI GPT-4o / Gemini API): Rejected due to ongoing per-token operational costs violating the zero-cloud-AI-cost constraints.

## Consequences
- Positive:
  - Eliminates cloud AI operational expenses.
  - Keeps floor-plan data on-premise.
  - Isolates AI failures so core booking features remain operational (DG-07).
  - Allows mocking IVLMClient in CI/PyTest (DG-10).
- Negative:
  - Natural-language and floor-plan queries depend on the librarian's workstation being powered on and running the local API wrapper.
